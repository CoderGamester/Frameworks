# Frameworks (Unity Host Repo) - AI Agent Guide

## 1. Repo overview
This repository is a **Unity 6 host project** used to develop, test, and validate multiple GameLovers UPM packages.

Most packages live under `Packages/` and are included as **git submodules** (see `.gitmodules`).

## 2. Key rules / standards

### 2.1 Project & language baseline
- **Unity**: 6000.0+
- **Render pipeline**: this host project is **URP-only**. The pipeline of record is `Assets/Settings/URP-Mobile.asset` (+ `URP-Mobile_Renderer.asset`), assigned in `GraphicsSettings.defaultRenderPipeline` and all 6 `QualitySettings` levels; color space is Linear. Only `com.gamelovers.uiservice` declares a hard `com.unity.render-pipelines.universal` dependency — its `Runtime/Rendering/` presenter features (camera stacking, render-texture targets, backdrop blur) genuinely need URP types. `com.gamelovers.gamedata`, `com.gamelovers.services`, `com.gamelovers.statechart`, `com.gamelovers.googlesheetimporter`, and `com.gamelovers.mobileservices` are **deliberately** pipeline-neutral (verified: zero rendering API references in any of them) and stay installable in BiRP/HDRP projects — do not add a URP dependency to any of them without the same justification `uiservice` has. Consumers who import a `uiservice` sample into a BiRP/HDRP project will see a missing-script warning on the sample scene's Main Camera (`UniversalAdditionalCameraData`); this is expected and accepted.
- **C#**: C# 9.0 syntax; **explicit namespaces** (no global usings)
- **Assembly boundaries**:
  - Runtime code must not reference `UnityEditor`
  - Editor tooling must stay under `Editor/` and Editor assemblies
  - **Sample asmdef boundaries**: Unity disallows asmdef-defined assemblies from referencing `Assembly-CSharp` (and vice-versa) in either direction. When a UPM sample's editor code uses sample runtime types in a generic constraint or `using` (e.g. `class XImporter : AssetsConfigsImporter<SampleEnum, AssetT, SampleSO>`), the sample runtime files MUST live in their own `*.asmdef` so the sample editor asmdef can reference them. Symptom of getting this wrong: `CS0246: type ... could not be found` from inside the sample editor assembly even though the type is right next door. Note also that asmdef references are NOT transitive — if a sample (or any consumer) touches an API that surfaces a type from a third package in its return shape (e.g. `AssetConfigsScriptableObject.Configs` returning `List<Pair<TId, AssetReference>>`, where `Pair<,>` lives in `GameLovers.GameData`), the consumer asmdef must reference that third package directly. Reference: `Packages/com.gamelovers.services/Samples~/AssetResolver/` ships both a runtime asmdef and an editor asmdef, the editor asmdef references the runtime asmdef, and both reference `GameLovers.GameData` for `Pair<,>`.
  - **`CS0012` depends on where the BASE class lives, not on whether the type "uses" the other assembly.** Calling a static member needs the external reference only when the type's base class is defined in that assembly: `UiBackdropBlurPass : ScriptableRenderPass` requires the URP reference even for an all-`bool` static method, while `UiCameraStackFeature : PresenterFeatureBase` (base in the same assembly) does not, no matter how much URP the rest of the class touches. Corollary: do **not** move code around to keep a test asmdef dependency-free. Decide the assembly's dependencies on their merits, then let placement follow — a URP-only package's test assemblies referencing URP is honest, and the alternative distorts where code lives.
- **UPM dependency changes need consumer evidence.** Adding or removing a dependency is not proved by a source grep or by the development host's resolved package list: unrelated packages can keep it installed. Map the exact API references to their owning runtime, Editor, test, or sample assemblies; inspect availability in every supported editor stream; then import affected `Samples~` entries into clean hosts and record each host's direct manifest, resolved lock, compile result, and behavior. A removed dependency is proven absent only in the clean consumer graph, or attributed to a different dependency chain.
- **Compatibility words name different evidence.** `package.json.unity` is the minimum editor floor; a reference stream is a selected family; a validated editor is one exact patch with current attributable evidence; and the primary development editor is neither of those. Matrix outcomes are `PASSED`, `FAILED`, or `NOT VALIDATED`. Licensing, network, unavailable-editor, and harness failures are `NOT VALIDATED`, never package failures or passes. Do not claim untested intermediate or future Unity 6 streams.
- **Validate current source and published installation separately.** A clean host using the workspace package proves the current tree; a second clean host using the exact pinned README Git manifest proves the install path. Never record a workspace code identity for a run that actually installed a remote tag. Git UPM dependencies are not transitively resolved from arbitrary Git repositories, and embedded host packages can mask that defect.
- **Conditional compilation stays at real platform boundaries.** Use `#if UNITY_EDITOR` / platform symbols where an API is unavailable or behavior genuinely differs. Keep shared validation, state transitions, ownership, and public contracts outside the branches. Repeated conditionals that encode the same semantic split belong behind one backend or boundary method; do not scatter editor policy through every public method.
- **Owned resources require an explicit lifetime contract.** A type that owns a Unity object, native handle, callback registration, coroutine host, or global subscription must define idempotent teardown and consistent post-disposal behavior. Stateful services whose backing resource is destroyed throw `ObjectDisposedException` from public operations after disposal; stateless facades and value-like helpers do not gain disposal guards merely for uniformity.
- **Do not release shared global facilities without ownership.** A component may clean up its own subscriptions, but it may disable a process-wide/static facility only when ownership is exclusive or acquisition is reference-counted. Lifecycle tests for such code must include at least two concurrent owners plus an external-release path.
- **C# loop-variable closure rename**: when renaming a `foreach` iteration variable that is captured for a closure (e.g. `foreach (var X in list) { var captured = X; btn.clicked += () => Use(captured); }`), `replace_all` every body reference — partial renames of only the `foreach` declaration leave compile errors (`CS0103: The name 'oldVar' does not exist`) on body lines that still reference the old name. The compiler error points at the body usages, not the declaration, so grep the full method body before considering the rename complete.

### 2.2 Evidence & verification
- **An exit code is not evidence — the artifact is.** Delete the expected output *before* a run, then require it to exist afterwards. A tool that fails can leave a previous run's file in place, and reading it yields confident, wrong answers attributed to the wrong input.
- **Prove freshness before reading a generated file.** Check its timestamp against the run that supposedly produced it. A report that predates your change describes a codebase that no longer exists.
- **Prove attribution before acting on a result.** When a result must map back to a specific input, verify the identifier is unique. Ambiguous keys (duplicate names across scopes, parameterized cases whose reported name differs from the declared one) mis-attribute silently rather than erroring.
- **A verifier's own PASS is not evidence — make it print the identity of what it compared.** The freshness and attribution rules above assume the artifact is wrong; this is the case where the *checking tool* is wrong, substituting one input for another and reporting success over it. A pass verdict about unnamed inputs is unfalsifiable, so any gate that claims two things agree must name both. Recorded instance: `Tools/test-all.sh compare` printed `BOTH ENVIRONMENTS GREEN` having compared the batchmode run with itself, because both halves write the same results path and it re-read that path at compare time. It now prints `distinct runs: batch=… editor=…`, and *that line*, not the verdict, is the evidence.
- **A measurement tool is unverified code — polarity-test it before its numbers drive any edit.** The rule above covers a verifier that *compares*; this covers one that *counts*. A static-analysis tool's false negatives are invisible and its false positives cause destructive edits, so a fixture must assert both directions — cases that MUST be flagged and cases that must NOT be — and the totals must reconcile against an independent method (grep, a second query) before the findings are acted on. Recorded instance: `Tools/style-audit.py` needed nine separate corrections, five of them after it was committed and being trusted. The worst was silent both ways: an auto-property with an initializer (`public List<T> Foo { get; } = new();`) flushed twice and the initializer tail inherited the property's doc lines, emitting a phantom unnamed private field — acting on that finding would have **deleted legitimate property documentation**. A second, `<param>`-shaped one applied effective accessibility to only 2 of 13 rules, which was about to produce summaries on effectively-private members, i.e. the exact opposite of the rule being enforced.
- **A comparison must prove its inputs are non-empty.** A diff of two empty streams passes, and is indistinguishable from a real pass unless the check prints what it read. Recorded instance: `head -n -1` does not exist on BSD/macOS, so an extract produced nothing on both sides and the guard printed `IDENTICAL — quotes remain valid` over two empty files. Print the byte count or the line count alongside the verdict; that line, not the verdict, is the evidence.
- **Verification runs are immutable and self-identifying.** Never overwrite a prior run's log, report, screenshot, or resolved lock in place. Give each attempt a run identifier and record source identity, full tool/editor version, input paths, output paths, and non-empty byte counts. Preserve failed attempts under their own identities; renaming an old artifact to the current expected path is not a rerun.
- **Compatibility evidence lives with test evidence.** Store run-identified compatibility attempts under `.test-all/compatibility/<run-id>/`, not a new top-level evidence convention. A generic batch runner may establish only the gates it actually executes; UI screenshots, native platform compilation, importer fixtures, and Editor-only behavior remain `NOT VALIDATED` until separately observed.
- **Read the failure artifact before forming a hypothesis.** A plausible cause proposed before the actual output is read is a guess wearing a lab coat, and it sends the investigation down a confident wrong path. Recorded instance: a test failure was attributed to concurrent-harness contention when the real cause was deterministic and visible in the first line of the report. Get the failing names and messages first; theorise second.
- **Never write "verified", "confirmed" or "tested" without a recorded observation.** Applies equally to code comments, docs, commit bodies and reports to the user. An unearned claim is worse than no claim: it stops the next person checking.
- **Count, don't estimate, before quoting a number.** If a number will be acted on, produce it with a command.
- **Validate a rule against the existing corpus before codifying it.** A threshold the codebase violates on the day it is written teaches everyone to ignore the document. **The reactive half: when an audit reports mass violations, suspect the rule before the code** — and treat "the best example in the codebase is the top offender" as near-proof the rule is wrong. Recorded instance: a §6.6 audit opened at 912 findings, of which ~58% were spec defects rather than drift; `Runtime/IUiService.cs` was simultaneously the most carefully documented file in the repo and the single largest source of `<param>` violations, because the rule banned the tags outright instead of scoping the ban to non-consumer-facing code. Rewriting the rule took the count from 912 to 551 before a line of code was touched; a further slice of the remainder then proved to be defects in the checker rather than real findings. See the `code-standards-audit` skill for the triage.
- **Checkpoint before a destructive experiment.** `git checkout` / `restore` / `reset` revert to HEAD, not to your last edit — they will silently discard *other* uncommitted work in the same file. Commit or stash first, especially before any mutate-and-revert loop.
- **When a finding resists the expected remedy, classify it before acting, and require proof of the class.** Heterogeneous findings need different actions; applying one uniform response destroys real signal. Concrete instance: the A5 / D2 / UNFALSIFIABLE verdict table in each package's `Tests/AGENTS.md` §2.
- **Keep the verifier separate from the author.** Self-review reliably misses the bug class you just wrote. Where correctness matters, have a different agent (or a later, adversarial pass) re-derive the result rather than confirm it.
- **"It compiles and the suite is green" is NOT verification for anything with visible output.** Rendering, camera setup, UI layout, shaders, animation: if the change is supposed to make something appear on screen, you have to look at the screen. Recorded instance: `UiCameraStackFeature` shipped having never rendered a single pixel, past 284 passing PlayMode tests. Use the `unity-play-verify` skill to drive Play Mode, capture the real Game view, inspect the image, and record attributable evidence.
- **Screenshot existence is not visual evidence.** A screenshot must be fresh, attributable to the current run, and inspected or independently checked for the expected rendered landmarks. Non-zero byte size, valid dimensions, or a verifier's `PASS` cannot distinguish the intended UI from a uniform camera-clear frame, a stale image, or the wrong Editor window. Record the scene, selected view, resolution, orientation, and capture source; reject nearly uniform images and captures missing task-specific landmarks. Use the `unity-play-verify` skill for this workflow.
- **Cached UI queries must be visibility-scoped.** A persistent shell keeps hidden pages in the same visual tree, so `root.Q(...)`, `Query<Label>().First()`, and equivalent global queries can return valid elements from an inactive page. Query within the selected page root, verify its display state and relevant ancestors, and assert exactly one selected destination before attributing text, bounds, or interaction state to what the user sees.
- **A test that asserts registration does not prove effect.** `Assert.IsTrue(baseData.cameraStack.Contains(overlayCamera))` passed while URP silently skipped that camera for being disabled. Membership, subscription, "was added to the list", "the request is registered" — all of these can be true while nothing happens. Assert the consequence, or at minimum the precondition the engine actually checks (`camera.isActiveAndEnabled`, not `camera != null`). Note this is a *coverage* gap, not a test-strength gap: mutation testing (`empirical-audit`) proves an existing assertion is falsifiable, and cannot tell you the assertion is about the wrong thing.
- **Test assemblies compile only during a test run.** They carry `defineConstraints: ["UNITY_INCLUDE_TESTS"]`, so a plain `-quit` editor open does not compile them. A warning or error count taken from such a run **excludes all test code** — it is a partial number, not zero. Recorded instance: a reported "0 warnings" hid a `CS0618` obsolete-API warning in a test file for several commits. Take counts from a `-runTests` log.
- **A script edited on disk while the Editor is open has NOT been recompiled.** Invoking a menu item or entering play mode immediately after writing the file executes the previous assembly, silently and successfully. Force it — `AssetDatabase.ImportAsset(path, ForceUpdate)` then `CompilationPipeline.RequestScriptCompilation()` — confirm `IsCompiling == false`, and prove the new code ran by checking for output only the new version produces. Recorded instance: a sample generator was run twice against a stale assembly, both times reporting success while emitting the old layout.
- **Check what the engine already provides before writing the feature.** Three cheap checks, in order: (1) is it an authorable serialized property (probe `SerializedObject` field names — `Camera.m_TargetTexture`, `PanelSettings.m_TargetTexture` are both Inspector fields, so "render UI to a texture" needs no code at all); (2) does the pipeline ship it (URP's `FullScreenPassRendererFeature` covers most custom full-screen passes); (3) does the engine now do it natively (`PanelRenderMode.WorldSpace` obsoletes UI-Toolkit-to-RenderTexture entirely). Skipping this produced six types across four review rounds that were all subsequently deleted as unnecessary.

### 2.3 Tooling & environment
- **`Tools/` holds the repo's repeatable scripts** (`coverage.sh`, `coverage-summary.py`). It is not referenced anywhere else in this guide — check it before writing a new one-off script.
- **One Unity project = one lock.** `unity test` takes a project-wide lock, so no two runs can overlap. Parallel agents must not invoke Unity; parallelise analysis and serialise execution.
- **An MCP timeout says nothing about whether the Editor is running.** A starting Editor has not attached the bridge yet, so `Unity_RunCommand` times out exactly as it would if nothing were running. The authoritative signals are `pgrep -f "Unity.app/Contents/MacOS/Unity"` **and** `Temp/UnityLockfile`. Note that Unity Hub, `UnityLicensingClient`, and the `~/.unity/relay/*` MCP helpers all match a loose `grep -i unity` and are **not** the Editor — they hold no project lock. Recorded instance: "Unity NOT running" was reported from a single MCP timeout and contradicted by `pgrep` minutes later. To open the Editor headlessly and wait for it properly, use `Tools/test-all.sh editor-open`.
- **Resolve Unity by project, not bundle identity.** Multiple Unity versions and projects share the same macOS bundle identifier, and GUI automation can focus an unrelated window. Before opening, focusing, clicking, quitting, or terminating an Editor, match its command-line project path to the project's `Temp/UnityLockfile`. Never force-terminate an Editor owned by another project; use a separately identified clean host when the intended window cannot be targeted safely.
- **`Unity_RunCommand` snippets: one top-level class, no nested types, no NUnit types.** The tool rewrites your code into its own namespace, which hoists a nested `private` class to namespace scope and fails with `CS1527` (*"Elements defined in a namespace cannot be explicitly declared as private"*). Its compilation unit also does not reference `nunit.framework`, so touching `ITestResultAdaptor.ToXml()` — or anything else returning `TNode` — fails with `CS0012`. Read results from the artifact file on disk rather than from an `ICallbacks` implementation; that also survives the domain reload entering PlayMode.
- **Unity CLI passthrough needs the project argument before `--`**: `unity test . --mode EditMode -- -flag`. Omit the `.` and the first passthrough flag is swallowed as the project path (`Not a Unity project ...`).
- **Unity Code Coverage needs `-debugCodeOptimization`, always.** Without it Unity compiles Release and emits far fewer sequence points — measured `MathfloatP` 1002 → 637 coverable lines, a uniform ~0.6 shrink across every class. The percentage still looks plausible, so the error is silent. Sanity check after touching the run: `MathfloatP` must report ~1002 coverable.
- **A coverage run writes multiple numbered files; `TestCoverageResults_0000.xml` is a zero-hit structural pre-pass** (0 visited sequence points vs 4391 in `_0001`). Never sum the numbered files — read `Report/Summary.xml`, which ReportGenerator's `MultiReportParser` merges correctly. Summing them once produced a wrong baseline that had to be retracted.
- **Report the runtime/Editor split, not the combined figure.** Editor assemblies are ~48% of coverable lines and near-zero *by policy* (the ACCEPTED (iii) rows in each `Tests/AGENTS.md` §13), so the combined number can never meaningfully move. `Tools/coverage-summary.py` prints all three; steer by runtime.
- **Unity Code Coverage is sequence-point only**: there is no branch coverage, `nPathComplexity` is emitted as `0` for every method, and CRAP is therefore systematically optimistic. Assembly filters are contains-matched — `-*Tests` does NOT exclude `X.Tests.PlayMode`; use `-*Tests*`.
- **Mutation-testing records belong under `.test-all/rcr/`, never `/tmp`.** The `empirical-audit` harness records which mutation reddened which test; that is the only thing that distinguishes "observed RED but the annotation write-back was lost" from "never probed", and from source alone the two look identical. `/tmp` gets cleared, so those records are perishable in a way the conclusions drawn from them are not. Recorded instance: 11 annotations were recoverable only because `/tmp` happened not to have been cleared yet. The directory is gitignored and carries a `README.md` with the two file schemas and the rule that prepared annotation text must never be written without a matching `RED-OK` for that test.
- **External APIs**: when investigating third-party sources (Unity packages, UniTask, Addressables), prefer local UPM cache under `Library/PackageCache/` when available.

### 2.4 Git & submodules
- **Never author or commit package work on a detached submodule `HEAD`.** Before the first mutation, identify the intended package branch, prove the current commit is its ancestor or tip, attach the worktree, and verify the upstream. A commit existing in the object database is not enough if no branch retains it.
- **Serialize nested-repository Git mutations and inspect partial success.** Branch moves, checkouts, commits, and pushes across submodules write different Git directories but still form one host operation. Run them one package at a time, re-read branch/status after any interrupted batch, and resume only the operations that did not complete.
- **Unity `.meta` files in git**: when moving or renaming assets, `git mv` both the asset and its `.meta` to preserve GUIDs. Newly created Unity-visible files and folders (including sample READMEs and `Editor/` folders) must receive stable, unique `.meta` files before the same change is committed. Prefer letting the intended Unity editor generate them, then inspect and stage them explicitly; do not defer metadata to an unrelated follow-up commit.
- **Opening the Editor dirties `ProjectSettings/ProjectSettings.asset`.** Unity syncs the Android `scriptingDefineSymbols` list to match Standalone (currently adding `SENTIS_ANALYTICS_ENABLED`), so the file shows as modified after any editor open even when you changed nothing. Expected churn — do not fold it into an unrelated commit, and do not go looking for what caused it.
- **Stage explicit paths; never `git add -A` or `git add .` when another agent may be working.** With a concurrent session this is correctness, not hygiene: `add -A` sweeps whatever else is in the tree into your commit, under your message. Recorded instance: a concurrent session's `add -A` absorbed this session's uncommitted `uiservice` doc edits into its commit `7fa2077` ("docs+test: Smoke RCR exemption…") and a `Tools/` fix into `a5151f5`, both unrelated messages; in the other direction, staging explicit paths is the only thing that kept its 98-line `MathfloatPTest.cs` out of an unrelated `gamedata` docs commit. Verify with `git diff --cached --stat` before every commit, and check `git status --porcelain` for files you did not touch. Note the exception below — a `reset --soft` squash genuinely needs `add -A` first, so do that one on a quiet tree.
- **A scripted rewrite must preserve the file's UTF-8 BOM.** Reading with `utf-8-sig` and writing with `utf-8` strips it silently; nothing compiles differently and no test fails. Prove it by comparing the first three bytes against HEAD (`git show HEAD:<file> | head -c 3 | xxd -p` versus the same on disk) for every file the script touched. Recorded instance: a doc-comment pass de-BOM'd `RngService.cs` and `VersionServices.cs`, visible only as a `-﻿using System;` line in the diff.
- **Squashing with `git reset --soft`**: before running `git reset --soft <base>`, always `git add -A` any working-tree changes. `--soft` preserves the index as-is and does NOT fold in unstaged edits — a squash done without this step will silently drop working-tree-only changes. Verify via `git diff --cached --stat` before the commit.
- **Deleting tracked files inside a submodule**: `git rm Packages/<pkg>/<file>` from the parent repo fails with `fatal: pathspec '...' did not match any files` — the parent doesn't own paths inside a submodule. Always run `git -C Packages/<pkg> rm <relative-path>` from the parent (or `cd` into the submodule first). If the file has working-tree modifications (e.g. you edited it earlier in the same session before deciding to delete), the plain form errors with `the following file has local modifications`; resolve with `git -C Packages/<pkg> rm -f <relative-path>` when the intent is to discard both the edits and the file.

### 2.5 Testing discipline
- **A green run is only green in the environment that produced it.** Unity batchmode and the Editor are different environments, and the difference is not cosmetic: **batchmode never instantiates the URP renderer**, so `ScriptableRendererFeature.Create()` never runs and any code branching on "is this renderer feature installed" silently takes the *not-installed* path. Anything touching URP, rendering, Addressables catalog state, or imported samples must be verified in **both** before it is called verified. Recorded instance: five `UiBackdropBlurPresenterFeatureTests` passed batchmode three separate times and failed 5/5 in the Editor — the fixture had hard-coded the absence of a renderer feature the project actually installs. See A6 in each package's `Tests/AGENTS.md` §1.
- **Running the Editor suite is cheap — use it.** `Tools/test-all.sh` runs batchmode EditMode + PlayMode and then the Editor PlayMode suite via `TestRunnerApi`, and refuses to report success unless both agree. The Editor half is driven headlessly through the unity-mcp `Unity_RunCommand` tool, so "I could only run batchmode" is not a reason. Note the Editor must be open for that half and closed for the batchmode half — they contend for the same project lock.
- **Both halves write the same `persistentDataPath/TestResults.xml`, so snapshot the Editor result before running batchmode.** `Tools/test-all.sh editor-save` does it; skip it and batchmode silently overwrites the Editor artifact, after which `compare` reads the batch run twice and prints `BOTH ENVIRONMENTS GREEN` having compared one environment with itself. Recorded instance: a compare that "passed" while the Editor file it claimed to read had a `start-time` seven minutes older than the run it was attributed to. `compare` now fails when the two files share a `start-time`, but the ordering is still the real fix — the guard only catches the collision, it cannot recover the lost artifact. It also stamps a `code_id` per run and fails when the two differ, because distinct start-times prove two runs happened and not that both ran the same code. That id digests **content** (every compiled `.cs` / `.asmdef`), not `HEAD` — a commit-based id fires whenever the halves are committed between runs even though every compiled byte is identical, and a gate that cries wolf is one people learn to ignore.
- **`LogAssert.Expect` does not suppress console output**: `LogAssert.Expect(LogType, message)` only consumes an expected log for the NUnit pass/fail decision. The log still streams to Unity's Editor console during the run — expected errors and warnings printing alongside a green test suite is normal, not a regression. Do not try to "silence" such logs by wrapping Debug calls; the log-assertion path is the intended contract.
- **`InternalsVisibleTo` for Unity test-assembly access**: Unity tests in a separate `*.Tests` assembly cannot see `internal` members of their source assembly. Prefer adding an `AssemblyInfo.cs` at the source assembly's root folder with `[assembly: InternalsVisibleTo("<SourceAsm>.Tests")]` over widening the member to `public`. One `AssemblyInfo.cs` is needed per assembly that must grant cross-assembly internal access. Reference: `Packages/com.gamelovers.services/Runtime/AssemblyInfo.cs` (Runtime→Editor) and `Packages/com.gamelovers.services/Editor/AssemblyInfo.cs` (Editor→Editor.Tests).
- **`.audit-history.md` is local-developer state, never committed**: the `unity-tests-audit` skill writes a per-package `.audit-history.md` at the package root (`Packages/<pkg>/.audit-history.md`) on every audit run. This file is **gitignored at every level of the repo** — every package's `.gitignore` carries a `.audit-history.md` line, and the host root `.gitignore` carries both `.audit-history.md` and `**/.audit-history.md` for nested-path defence-in-depth. New packages added to `Packages/` MUST receive the same `.gitignore` line (no exceptions — preventive, even if no audit has been run yet). If an audit-history file was tracked before this convention applied, untrack with `git -C Packages/<pkg> rm --cached .audit-history.md` (the `--cached` keeps the file on disk; pair with the `.gitignore` line so it stays untracked). Audit "expand" commands read this local-only file; cross-developer audit history is never shared via VCS.

- **Never mutate a `ScriptableObject` asset at runtime.** In the Editor the change persists to disk, silently altering authored state for the whole project; at runtime it reconfigures every other consumer of that shared asset. This has bitten twice: writing `PanelSettings.targetTexture` (a `PanelSettings` asset is a *panel*, shared by every `UIDocument` pointing at it) and a proposed runtime write to a `ScriptableRendererFeature`'s serialized look settings. The working pattern is a **static, non-serialized override** exposed alongside the authored value, cleared by a sentinel and reset via `[RuntimeInitializeOnLoadMethod]` (statics survive between play sessions when Domain Reload is disabled). Reference: `UiBackdropBlurRendererFeature.IterationsOverride` / `EffectiveIterations` / `AuthoredIterations`. Cloning the asset per consumer is the wrong fix — it multiplies panels/instances and breaks whatever cross-instance ordering or batching the shared asset provided.

### 2.6 Editor tooling & UIToolkit
- **Editor namespace collision**: Editor scripts placed in a sub-namespace ending with `.Editor` (e.g., `GameLovers.X.Editor`) MUST qualify the Unity base class as `UnityEditor.Editor`. A bare `Editor` resolves to the enclosing namespace's own `.Editor` child (a namespace), not the Unity type, producing `CS0118: 'Editor' is a namespace but is used like a type`.
- **Editor UI stack**: for new editor tooling (windows, inspectors, property drawers) in this framework, prefer UIToolkit — `EditorWindow` + UXML + USS + Unity 6 `TabView` for windows; `CreateInspectorGUI()` / `CreatePropertyGUI()` for inspectors and drawers. IMGUI (`OnInspectorGUI` / `OnGUI`) is acceptable only for maintenance of existing tools; do not default to it for new work. Reference implementation: `Packages/com.gamelovers.services/Editor/Explorer/`.
- **One interaction stream has one owner.** Do not combine UI Toolkit pointer capture, EnhancedTouch classification, and manual scrolling for the same touch sequence. Native `ScrollView` owns touch button cancellation, dragging, velocity, inertia, and springback. A Game-view mouse-drag helper, when explicitly required, handles mouse only and ignores touch and wheel streams.
- **Swipe recognition is not continuous scrolling.** A recognizer with duration, distance, or direction classification cannot transport page scrolling because it may stop emitting without a terminal callback. Every custom pointer owner must release capture and reset state on Up, Cancel, owned CaptureOut, detach, disable, application pause, and focus loss. Never treat EnhancedTouch finger indexes as UI Toolkit pointer IDs.
- **UIToolkit `Foldout` header customization**: `foldout.Q<Toggle>()` returns the clickable header row; you can `.Add()` siblings (e.g. action buttons) to it, but click events bubble up to the toggle and would also collapse/expand the foldout every time the user fires the action. Always insert `RegisterCallback<ClickEvent>(evt => evt.StopPropagation())` on every action element added to the toggle row. Reference: `Packages/com.gamelovers.services/Editor/Explorer/Tabs/MessageBrokerTab.cs` — per-message-type `Unsubscribe All` lives on the foldout header next to the type name + count.
- **`EditorWindow` does not expose `schedule`**: `schedule` (`IVisualElementScheduler`) lives on `VisualElement` only. Calls like `schedule.Execute(() => …).StartingIn(ms)` inside an `EditorWindow` method body fail to compile with `CS0103: The name 'schedule' does not exist in the current context`. Route through `rootVisualElement.schedule.Execute(...)` instead — the panel's own scheduler lives as long as the window. `VisualElement`-derived editor types (e.g. `ServiceTab` / `MobileServiceTab` explorer tab bases) inherit `schedule` directly and can call it bare.
- **`DeviceSimulatorPlugin` platform sync**: when extending Unity's Device Simulator via `UnityEditor.DeviceSimulation.DeviceSimulatorPlugin` and you need to track the user's selected device profile (iOS / Android), prefer polling `Application.platform` on a `VisualElement.schedule.Execute(...).Every(500)` cadence over subscribing to `DeviceSimulator.deviceChanged`. The event's delegate signature is documented inconsistently across Unity 6 minor versions (6.0 / 6.2 / 6.3+ ScriptReference pages describe the event without showing the delegate type), so version-pinned subscriptions risk silent breakage on Unity upgrades. Unity's Device Simulator spoofs `Application.platform` for device-profile picks (`RuntimePlatform.IPhonePlayer` / `RuntimePlatform.Android`) — polling is outcome-equivalent and version-agnostic. Note also that `DeviceSimulatorPlugin` subclasses are auto-discovered across all editor assemblies (no `[Attribute]`, no registration). Reference: `Packages/com.gamelovers.mobileservices/Editor/Explorer/DeviceSimulatorPanel/MobileServicesDeviceSimulatorPlugin.cs`.
- **UIToolkit numeric field label-width pitfall**: the `IntegerField(string label)` / `FloatField(string label)` constructor first arg is a label rendered *inside* the widget at the top, eating most of the interior width — multi-digit numbers render off-screen even at sane widget widths (~130 px). For compact rows, build the row as `Label("Field: ") + naked IntegerField()/FloatField() + (optional) Slider/SliderInt`. Pair the slider with the field via bidirectional `RegisterValueChangedCallback` + `SetValueWithoutNotify` to avoid feedback loops. Reference implementations: `Packages/com.gamelovers.services/Editor/Explorer/Tabs/TimeTab.cs` AddTime row and `Editor/Explorer/Tabs/RngTab.cs` Peek-N + Set-counter rows.

### 2.7 Documentation, samples & versioning
- **Package README accuracy**: when updating or auditing a package `README.md`, always verify every code example, component name, feature claim, and file-tree reference directly against the package's own `AGENTS.md` §2/§3 and the actual `Runtime/` source files before writing. Fabricated or stale examples are a known risk; a recurring drift pattern is README-level marketing copy (types or subsystems that no longer exist in source) outpacing AGENTS/Runtime reality — e.g. the `mobileservices` README once marketed `PointerInputManager` / `Controls/` / "Input System Integration" while the source uses `EnhancedTouch` only.
- **Dependency drift**: when a package's `package.json` dependency changes, cross-check both `README.md` and `AGENTS.md` for stale references to the old package name or version.
- **Package descriptions state purpose, not compatibility.** Keep `package.json.description` focused on what the package does and its meaningful scope. Unity version numbers, validation status, badges, release labels, and marketing superlatives belong in neither the description nor package metadata; put compatibility in `unity` and the README evidence matrix.
- **README installation is a clean-host contract.** Resolve repository slugs from `.gitmodules`/canonical remotes, confirm exact tag syntax, and test the manifest shown to users. A development host that embeds sibling packages cannot prove a one-URL installation works.
- **README structure serves adoption decisions.** Prefer outcome, use/avoid guidance, compatibility/dependencies, pinned install, compile-ready first success, concepts/lifecycle/limitations, exact samples, troubleshooting, and support. Do not force exhaustive public-interface inventories or link end users to `AGENTS.md`; use deeper docs and `CONTRIBUTING.md` where appropriate.
- **Package samples**: for code-centric UPM packages (no scene hierarchy, no custom inspectors), inline README code examples are sufficient; a `Samples~/` directory adds maintenance burden without proportional value unless the setup requires a running scene.
- **App-like tabs switch views, not scenes.** When a sample promises persistent tabs or destinations, tab selection must not call `LoadSceneMode.Single`. Prefer one resident shell with cached page roots, one shared service context, and navigation outside page ScrollViews. Do not substitute additive loading when it would duplicate cameras, panels, services, subscriptions, or native side effects. Preserve independently opened legacy scene paths as thin initial-page wrappers when their GUIDs are contractual.
- **UPM sample copies require explicit synchronization.** `Samples~` is the package source of truth, while an already imported `Assets/Samples` copy does not update automatically. After changing package source, refresh the imported copy, compare the relevant files, force a fresh compile, and perform visual/input verification against the imported copy the host actually runs.
- **Console cleanup preserves actionable failures.** Remove routine sample/demo chatter, temporary input diagnostics, and expected-fallback logs before handoff. Keep unexpected initialization and operational errors unless another observable diagnostic channel replaces them; silently swallowing a genuine failure is not console cleanup.
- **Sample-scoped editor automation**: when a UPM sample needs editor-side automation (auto-Addressables wiring, asset post-processing, generated content, custom menus/inspector affordances), the editor scripts MUST live inside `Samples~/<Sample>/Editor/` with their own `.asmdef` — never in the package's main `Editor/` assembly. Three contracts to follow: **(1) Lifetime** — sample editor scripts ship as full Editor assemblies into consumer projects, so anything in the package main editor would orphan after sample deletion; one inside the sample folder goes away with the sample. **(2) UPM first-import chicken-and-egg** — an `AssetPostprocessor` shipped inside `Samples~/<Sample>/Editor/` compiles AFTER the import batch that brings it into the consumer's project, so it MISSES its own first invocation against same-batch assets. Pair it with an `[InitializeOnLoadMethod]` safety net, defer both entry points to `EditorApplication.delayCall` (asset modification during `OnPostprocessAllAssets` itself is unsafe), and write the setup state-based-idempotent so subsequent reloads are silent no-ops. **(3) Cross-editor-assembly decoupling** — the package's main `Editor/` assembly must NOT compile-time reference a sample-scoped editor assembly; invoke functionality across the boundary via `EditorApplication.ExecuteMenuItem("Tools/.../<verb>")` and guard the caller-side UI (e.g. an inspector button) with an asset-path check so the entry-point only appears when the inspected context belongs to that sample. Reference: `Packages/com.gamelovers.services/Samples~/AssetResolver/Editor/AssetResolverSampleSetup.cs` + `Packages/com.gamelovers.services/Editor/Inspectors/AssetConfigsScriptableObjectEditor.cs` (`IsAssetResolverSampleConfigs()` path-guarded button calling `ExecuteMenuItem`).
- **Sample build and native ownership**: use the `unity-package-sample-builder` skill for either a single-scene sample or a catalog-backed bundle. Unity-owned identities come from serialized object references; hand-authored asset GUIDs and sample-relative scene paths are forbidden in C# and shell lookup logic. Multi-scene automation uses one sample-owned typed `ScriptableObject` catalog discovered by type; a single-scene sample needs no catalog unless automation requires a serialized identity. Resolve current paths with `AssetDatabase.GetAssetPath` only at the point of use.
- **Preflight before sample mutation**: validate all serialized references, uniqueness/order requirements, production configuration, manual-management policy, and the exact build-activation predicate before changing Build Settings, Build Profiles, or generated files. A transient convenience default is not build authorization. Temporary overrides clone persisted configuration or start from a neutral all-disabled state, never dirty authored assets, and are cleaned after success, failure, and cancellation.
- **One native mutator, semantic output**: package production integration is the sole owner of Android/iOS generated-project mutation; an optional sample contributes declarative temporary requirements instead of a competing processor. Merge by semantic identity, preserve conflicting non-empty consumer values, save only changed files, declare callback order/ownership, and prove a second identical pass is duplicate-free.
- **Sample verification consumes authoritative artifacts**: orchestration scripts read sample source/display metadata from `package.json` and consume fresh, non-empty Unity-produced identity artifacts. They do not reconstruct scene paths or parse Unity YAML. Identity artifacts name their input and resolved key/path/GUID rows; acceptance covers missing/duplicate/null references, move/rename resilience, exact build activation, cleanup, and imported-sample deletion.
- **XML doc-comment verbosity tier**: lives in §6.6 "XML documentation rules" — `internal`, editor-only and sample methods and types take a single-sentence `<summary>`; public consumer-facing API takes the multi-line block form. Historical note: the tier was applied across `com.gamelovers.mobileservices` 2026-05-11 (~145 LoC of XML doc removed from 22 internal/editor-only files), and is the standing convention for the GameLovers package family.
- **Pre-publication versioning**: if a UPM package's current version has not been published/tagged yet, fold new work into the existing `## [X.Y.Z]` `CHANGELOG.md` section rather than creating a new version entry. Do not bump `package.json` `version` and do not add entries to `MIGRATION.md` until the version is actually published. Only create a new `## [X.Y.Z]` section when cutting an actual release.

## 3. Repo structure
- `Assets/`: Unity project assets used for development/testing.
  - `Assets/Samples/`: **imported package samples** (preferred place to work when validating/changing sample content in this host project).
- `Packages/`: Embedded UPM packages (mostly submodules).
- `ProjectSettings/`, `UserSettings/`: Unity configuration.

## 4. Samples workflow (priority order)
When a task references a sample scene/script:
- **1) Locate and edit the authoritative package sample** under `Packages/<package-name>/Samples~/...` for embedded/submodule packages.
- **2) Treat `Library/PackageCache/<package-name>@<version>/Samples~/...` as read-only evidence** for external packages; do not patch the cache.
- **3) Refresh the matching `Assets/Samples/` copy after package source is correct.** This imported copy is what the host project runs, but Package Manager does not update it automatically.
- **4) Compare source and imported copies, force a fresh compile, and perform visual/input verification against `Assets/Samples/`.** Never leave the package source and imported verification target behaviorally divergent.

If a package folder under `Packages/` is empty, initialize submodules:

When editing a package, treat it like its own repo:
- Make changes inside `Packages/<package-name>/`
- Update that package's `README.md` / `CHANGELOG.md` when behavior or API changes
- Prefer contributing upstream to the package repository

## 6.5. CHANGELOG dialect
All packages follow [Keep a Changelog](http://keepachangelog.com/en/1.0.0/) with `## [X.Y.Z] - YYYY-MM-DD` section headings. Sub-heading style has drifted across the family (some packages use canonical `### Added`/`### Changed`/`### Fixed`, others bold-label `**New**:`/`**Changed**:`/`**Fixed**:`, one uses bold-label with no trailing colon). The canonical style going forward, used by the majority of packages, is **bold-label with a trailing colon**: `**New**:`, `**Changed**:`, `**Fixed**:`, `**Docs**:`. Use it for every new CHANGELOG section in every package; do not retroactively rewrite historical sections just to converge the dialect — that's cosmetic churn with no functional value.

The pending entry is the consumer-facing release record, not a commit summary:

- **Consumer-facing does not mean generic.** Give each independently useful capability or observable change its own concise bullet. Preserve public type and feature names when they help a Unity consumer understand, adopt, or migrate the change.
- **Initial, major, and consolidation releases need a feature inventory.** Under `**New**:`, use one labeled bullet per public subsystem rather than blending distinct subsystems into an umbrella sentence. Group implementation details that support the same outcome, not unrelated public capabilities.
- **Make impact explicit.** Breaking changes, removals, migrations, supported replacements, Unity/platform/render-pipeline baselines, required dependencies, sample-compilation changes, and observable runtime fixes must not be hidden inside generic prose.
- **Keep contributor mechanics out.** Omit individual test cases and counts, audit terminology, contributor files, CI cleanup, XML-comment mechanics, private helpers, internal refactors, and test-only seams. Automated coverage may receive one generic confidence bullet when it is a material release benefit. Documentation belongs only when it materially changes what consumers can successfully use.
- **Reconstruct from complete evidence.** Inventory `origin/master...origin/develop` across public API, runtime behavior, dependencies, compatibility, samples, migrations, and consumer docs. The current changelog and commit subjects are draft evidence and may omit or over-compress changes.
- **Edit only the pending region.** Merge `Unreleased` into the existing unpublished version, preserve every historical release byte-for-byte, and retain the file's BOM, CRLF/LF, and EOF convention. Date the entry for intended publication and recheck the date if release is delayed.
- **Synchronize release surfaces.** After committing and pushing a changelog change, update the existing package release PR body from that entry and re-read it to prove exact equality. An empty host-repository PR list says nothing: package PRs live in their submodule repositories. Require local `HEAD`, `origin/develop`, and the PR head SHA to match; never open a duplicate PR when the matching `develop` → `master` PR already exists.

Use the `unity-package-release` skill for changelog preparation, structural validation, PR-body synchronization, and publication. Its bounded changelog writer preserves historical bytes and its release driver enforces the package-repository identity and PR-head checks.

## 6.6. Code style & documentation

### General C# rules
- **No `goto`**; use guard clauses and early returns over nested `if`/`else`.
- **Prefer deletion over speculative code.** Remove dead fields, callbacks, config, branches, and abstractions; add code only for a current requirement or an enforced invariant. An interface with exactly one implementation and no plausible second is speculative.
- **Prefer generic, reusable helpers over caller-purpose-named ones.** Name shared utilities by what they do, not by the first feature that needed them.
- **Simulator and diagnostic tools act on the consumer's real instance.** A panel-owned throwaway service can preview generic UI, but it cannot claim to schedule, deliver, cancel, route, or mutate the running application's state. Use an explicit transient target/adapter contract owned by the sample or consumer, and make unregistering part of that target's lifetime.
- **Private fields use `_camelCase`** — never `m_*` (reserved for Unity's own serialized YAML names, which we don't control) and never `s_*` for statics; a private static field is still `_camelCase`.
- **Private methods use `PascalCase`**, never an `_underscore` prefix — that prefix is for fields only.
- **Private const strings** are plain `PascalCase`; never `c_` or `SCREAMING_SNAKE_CASE`.
- **`nameof(T)` over string literals** for type-name-derived paths (`Resources.Load`, `AssetDatabase.LoadAssetAtPath`, Addressables keys, log prefixes). A standalone `private const string FooPath = "Foo"` next to a type-derived load is the smell.
- **C# 9 syntax**: no file-scoped namespaces, no global usings, explicit namespaces.

### Code comments
- **Comments are for non-obvious rationale** — trade-offs, invariants, ordering requirements not enforced by the type system, workarounds for external bugs. Never narrate the obvious (`// Increment the counter`).
- **Never explain the change you are making.** Diff context belongs in the commit message; a comment describes the code's permanent state, not how it got there. Wrong: `// An earlier version cached this, which leaked a handler.` Right: `// Resolved twice per open, so it needs no caching.`
- **One sentence usually suffices.** Multi-paragraph rationale is a smell — split the function, rename for self-documentation, or move it to `docs/` behind a one-line pointer.
- **Prefer rewriting unclear code over commenting it.**
- **On a `private` member a comment is a last resort, and usually a design smell.** Write one only when the name and the body *together* still fail to convey the purpose. Needing one is evidence the member itself is wrong — rename it, split it, or restructure until the code states its own intent. A `//` that restates the signature is worse than none, because it advertises help the reader was never actually given. Removing a `///` block from a private member is **not** a licence to leave a `//` comment in its place: re-earn it against this bar, or drop it.

### XML documentation rules
- **NEVER documented — no exceptions.** Anything `private`: private methods, private fields, private properties, private events, and private or nested-private classes, structs and enums. **Accessibility is effective, not declared** — a `public` or `override` member of a private nested type is unreachable from outside that type, so it counts as private here and gets no `///` block either (that includes a bare `/// <inheritdoc />`). By the same rule, members of an `internal` type are internal, not public, however they are declared — which matters because interface members carry no modifier and default to `public`. Also **every constructor**, whatever its access, and generated code. If a symbol is `private` it gets no `///` block at all. Deleting one is **not** a licence to leave a `//` comment behind in its place — see the last bullet of **Code comments** above for the much higher bar a comment on a private member must clear. This is the most frequently broken rule in this repo; a doc comment on a private member is a defect, not a bonus.
- **Always documented**: `public` / `protected` / `internal` types (class, struct, interface, enum) and their methods, properties, events, and non-private fields.
- **The doc block goes ABOVE the member's attributes, never between them and the declaration.** A `///` block placed after `[MenuItem]` / `[MethodImpl]` / `[RuntimeInitializeOnLoadMethod]` does not attach to anything — no compiler error, no warning, and the member reads as undocumented forever. Conversely a plain `//` comment sitting between a `///` block and its declaration does *not* detach the documentation, so `// ReSharper disable once …` under a summary is fine. Recorded instance: an insertion pass anchored on the declaration line rather than the top of the attribute run and misplaced 9 summaries across two rounds; `Tools/style-audit.py` reports these as undocumented, and a scan for `///` immediately preceded by an attribute line catches them.
- **Form, by declaration kind**:
  - **Physical layout is independent of verbosity.** A single-sentence summary may still span multiple source lines. Use `/// <summary>Current zoom magnitude.</summary>` only when the complete line, including indentation and XML tags, fits within 120 columns. Otherwise use the normal `/// <summary>` / wrapped `///` content / `/// </summary>` block; never compress or weaken text merely to keep the tags on one line.
  - **Properties, events and fields** — use the inline form when the complete line fits within 120 columns; otherwise use the multi-line block.
  - **Methods and types on public consumer-facing API** — always the multi-line block form, even when the text would fit on one line.
  - **Methods and types that are `internal`, editor-only, or inside a sample** — keep the summary to one sentence, using the inline form only when the complete line fits within 120 columns. Longer sentences use the multi-line block and cross-reference `AGENTS.md` or `docs/<file>.md` rather than duplicating architecture text in the class header, so the rationale lives in one place instead of N class headers.
- **Enum values** use `//` inline on the same line as the declaration — never `/// <summary>` above.
- **`<remarks>`** only for non-obvious behaviour, invariants, or "why". Describe durable behaviour, not the current call graph.
- **`<param>`, `<returns>`, `<typeparam>`, `<exception>`** belong on **public consumer-facing API declarations** — the interface that declares the contract, or a public type with no interface to inherit from — where IntelliSense / Rider-hover discoverability is the load-bearing reason. Reference: `Packages/com.gamelovers.uiservice/Runtime/IUiService.cs`. An implementation of such an interface uses `/// <inheritdoc />` and repeats none of them. Do **not** add these tags to `internal`, editor-only, or private-implementation code — fold whatever matters into the `<summary>`. (`<paramref>` inside a summary is fine anywhere.)
- **`/// <inheritdoc />`** when implementing an interface member or overriding a documented base member; on a *type* that implements an already-documented interface it collapses to a single line. Confirm the base actually carries a `<summary>` first — `<inheritdoc />` aimed at an undocumented base yields empty IntelliSense with no compiler error, and reads as "documented" to any checker.
- **Exempt assemblies: `Tests/` and `Samples~/`.** Test fixtures and sample driver classes are `public` out of necessity, not as an API surface, and require no XML docs. Name the test so its declaration documents itself, and use the `//` ADMIT/RCR header that each package's `Tests/AGENTS.md` §2 mandates.

### Member ordering inside a type
Omit sections that don't apply, but keep this sequence: **public inner types → const fields → static fields → `[SerializeField]` fields → public fields → private fields → properties → constructor → Unity `MonoBehaviour` methods → methods by access**.

Methods by access, strictly: **public static → public override → public abstract → public → internal → protected → private**.

**`internal` is never interleaved with `private`.** An `internal` test-only helper lives in the contiguous `internal` block above the private methods, even when its only caller is two lines away — co-locating it hides which symbols are testable across assembly boundaries. When adding a member, place it by **kind then access**, never next to the related method.

## 7. Documentation policy
- Root `README.md` documents **this host repository** and links out to packages.
- Package-level `README.md` documents the **package** (install, usage, API, samples).
- Package-level `AGENTS.md` is the **contributor/agent guide** for that package (architecture, gotchas, workflows).
- **Never declare an external file authoritative unless something enforces the sync.** A "mirrored from X; if the two disagree, X wins" note rots the moment either side is edited, and then the local file is both untrustworthy and the only one anyone reads. Either mechanise the copy or own the text outright. Recorded instance: §6.6 claimed to mirror `~/Desktop/demons/AGENTS.md` and to defer to it; the two had already diverged in nine ways, including a dropped "when the content fits" qualifier on the properties rule that turned a sane guideline into 127 phantom violations. The claim was deleted and §6.6 is now owned here.
- **README size threshold**: when a trimmed package `README.md` would exceed ~350 lines, move deep API reference into a sibling `docs/` folder (flat `.md` files + a `docs/README.md` index). The README itself should stay lean: Why / Install / Quick Start / Services-at-a-Glance / Samples / Related docs / Contributing / Support / License. Reference implementations: `Packages/com.gamelovers.uiservice/docs/` and `Packages/com.gamelovers.services/docs/`.

## 8. Claude Code convention
Every package with an `AGENTS.md` also has a `CLAUDE.md` at the package root. `CLAUDE.md` is a thin wrapper that imports `AGENTS.md` via Claude Code's native `@AGENTS.md` syntax — it contains no duplicated content.

**This applies at every level, not just the package root.** A subfolder `AGENTS.md` (§6) gets a sibling `CLAUDE.md` wrapper too — a bare subfolder `AGENTS.md` is only found if its MUST-read pointer is followed, whereas a nested `CLAUDE.md` is auto-imported by Claude Code the moment work touches that directory. As of 2026-07-31 every package's `Tests/AGENTS.md` has a matching `Tests/CLAUDE.md`; keep that pairing whenever a new subfolder guide is added anywhere in the tree.

When creating a new package with an `AGENTS.md`, also create a matching `CLAUDE.md` following this template:

```markdown
# Claude Code Guide — <package-display-name>

This package's contributor/agent guide lives in `AGENTS.md`.
Claude Code will automatically import it below.

@AGENTS.md

## Claude-Specific Notes

- Treat `AGENTS.md` as the source of truth.
- If anything in this file appears to conflict with `AGENTS.md`, prefer `AGENTS.md`.
- For user-facing usage, see `README.md`.
```

For a subfolder guide, retarget the last two lines at the parent instead of the package root:

```markdown
# Claude Code Guide — <package-display-name> <Subfolder>

This folder's conventions live in `AGENTS.md`.
Claude Code will automatically import it below.

@AGENTS.md

## Claude-Specific Notes

- Treat `AGENTS.md` as the source of truth.
- If anything in this file appears to conflict with `AGENTS.md`, prefer `AGENTS.md`.
- For package-level architecture, see `../AGENTS.md`.
```

Also create a matching `CLAUDE.md.meta` Unity asset meta file (copy the `TextScriptImporter` pattern from any existing `AGENTS.md.meta`, with a fresh GUID).
